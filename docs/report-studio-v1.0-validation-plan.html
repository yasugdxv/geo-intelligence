この計画の位置づけ

Design → Evidence → Classification → Expert Synthesis → Report → Continuity → Monitoring → Need → Reassessment。Phase 0〜6でこのループは技術的に一周した。ここから先で問うべきは「さらに何を作るか」ではなく、専門家・実務担当者の判断品質と工数を本当に改善するかである。

検証期間中は新機能を追加しない。機能を増やすと「何が効いて品質が上がったのか」が分からなくなる。まず実運用で数本回し、人間がどこで修正するか・どこで迷うか・どこを信用しないかを集める。その結果を v1.1の要件 にする。評価は「良さそうだった」で終わらせず、事前に固定した合格基準（3章）と照らして GO / CONDITIONAL GO / NO-GO（6章）まで一気につなげる。
この計画は 2026-09-02 に v1.0-validation-plan baseline として固定した。 検証期間中は評価基準・Gate閾値・ルーブリックを直接編集しない。変更したくなった場合も本文を上書きせず、 巻末の Baseline Issue Log へ「評価基準自体に問題があった」こととして別記録する （評価結果と評価基準の変更を混同しないため）。
1

検証テーマ（3件）

性質の異なる3テーマを選び、それぞれ「旧フロー（手作業）」と「Report Studio」を同一期間データで並行実施し比較する。いきなり多数テーマには広げない。実施順は①→②→③固定。

THEME 01 · 実施順 ①

Zelenskyy / Ukraine

Actor中心 Calibration Case

主に見る観点: Actor Intelligence・Media Intelligence・Provenance・Continuity。開発テストで最も挙動を理解しているテーマのため最初に置く。この1本だけはスコアより「評価者がどこで迷うか」（Observed/Expert Contextの判別、修正箇所の特定、Review Requiredの解釈、同条件の線引き）を先に見る ——計画そのものの使いやすさの検証を兼ねる。

THEME 02 · 実施順 ②

Iran sanctions

政府・世論・反応

主に見る観点: 多主体・政府反応・Public Voice・Counterevidence・Watchpoint。Zelenskyyで計画の使い方が固まった後、未知の問題を探す。

THEME 03 · 実施順 ③

EUDR 等規制

規制・企業行動

主に見る観点: 規制→対応→行動→Business Implicationの比較分析。Stageの進行と企業行動への影響を正しく接続できるか。

2

評価5軸

最終的にこの5軸でv1.0を評価する。合格基準は「3. 合格基準」、詳細な観点は「4. 評価項目詳細」、記入は「6. 採点表」で行う。

01

Quality

専門家評価。中央評価の妥当性、論点の網羅性、推論の節度。

02

Efficiency

時間・工数・LLMコストを合算したTotal Costでの削減率。

03

Trust

Evidence traceability／provenance。Review Requiredの精度。

04

Operational Stability

失敗率・Review率。障害時のretry／resume／idempotency。

05

Intelligence Value

新しい論点・変化検出・判断支援としての付加価値。

3

合格基準（Go / Conditional Go / No-Go）

評価が終わってから基準を動かさないよう、判定条件を先に固定する。数値は初期値の例——実施前に確定させる。

軸合格基準（Gate）判定ロジック
Critical Issue は以下のいずれかに固定する（1件でもあれば、他の軸が満点でも Conditional Go 以下 とする）:
  • Evidenceにない事実
  • ObservedとExpert Contextの混同
  • 重要なCounterevidenceの脱落
  • 結論を逆転させる誤り
4

評価項目詳細

7つの評価ディメンション。それぞれ観点・測定方法・記録欄を定義する。

4.1 Report品質

Axis 01 · 最重要

従来の手作業フローと同じテーマ・同時期データで並行作成し、専門家が同一ルーブリックで評価する。単純な5段階評価だけでなく「どこを直したか」と重大度を残す方が、Expert AI改善には価値がある。Criticalの定義は 3. 合格基準 を参照。

評価者間クロスチェック: 3テーマ全部を複数人で評価する必要はない。1テーマだけ、別の評価者に同じ手順で独立して評価してもらい、それぞれ「7. 結果のExport」でJSONを書き出して突き合わせる。差が大きければ「AIの品質差」ではなく「専門家自身の見方の差」である可能性を疑う。
CALIBRATION MEMO — Iran / Strait of Hormuz（Zelenskyy代替・実施順①・FROZEN 2026-09-03）

Zelenskyyは実データが存在しなかった（DB上は検証用Fixtureのみ）ため、もともと②に予定していたIran/Hormuz（実記事13件、Bloomberg/CNBC/NPR/SCMP等）を①へ前倒しして実施。この1本目はスコアより、計画そのものの使いやすさと、Draft／Expert Review／Systemの品質をどう切り分けるかを見る。十分な学びが出たため、このケースはここでFreezeし、次の未知ケースで汎化性能を見る。

CALIBRATION MEMO — EUDR実装局面（Calibration #2・FROZEN 2026-09-04）

Hormuzが「地政学・危機／Evidence豊富」だったのに対し、EUDRは「規制・サプライチェーン／Evidence希薄（ClaudeによるWeb検索で新規persistした19件、本文はtitle相当のみ）」という構造的に異なるドメインとして意図的に選定。Sustainability crawler（articlesテーブル）は別アプリのため参照せず、Report Studio検証専用の新規themeへ実データ（実URL・実出典）のみを永続化して実行した。2ケースで十分な学びが出たため、ここで「Calibration」フェーズを終了しFreezeする——3件目には進まず、次は共通課題の修正（v1.1 Fix List）と、Cross-Narrative専用のTargeted Validationへ移行する。

4.3 Review Requiredの精度

Axis 03

Guardを強く作った分、本当に人間が見るべきところだけがReview Requiredになっているかが重要なKPIになる。

大量Evidence↓ ほぼ自動処理↓ 数件だけReview Required↓ 人間が重要箇所だけ確認

逆にREVIEW REQUIREDが頻発すると、結局人間の負荷が戻る。特にLLM分類の非決定性（同一Evidenceで結果が揺れる既知課題）はログを取る。

ログ項目記録
同じEvidenceでPASS/REVIEWがどの程度揺れるか
retryすると収束するか
特定dimensionで多発するか

4.4 Continuous Intelligenceの実運用精度

Axis 05 · 2〜4週間継続

Phase 4〜6は技術的には通ったが、時間を置かないと本当の品質は分からない。実テーマを2〜4週間継続し、New / Intensified / Reframed / Stable / Resolved の判定が人間の感覚と合うかを見る。Precision重視 ——最初から大量Alertを出すより「これが出たら見た方がいい」という信頼を作る方が重要。

4.5 Expert AIが本当に価値を足しているか

Axis 05 · A/B比較

同じEvidenceで比較する。見るのは文章の上手さではない。Observed Evidenceは両条件で完全に同一にする（詳細は5.0比較条件の固定）。

CONDITION A

Observed Evidenceのみ

→ Synthesis

CONDITION B

Observed + Actor Intelligence + Media Intelligence + Precedent

→ Expert Synthesis

4.6 Provenanceのユーザー理解

Axis 03 · ユーザーテスト

Observed Evidence / Expert Contextを技術的に分離できていても、ユーザーがUIを見て本当に違いを理解できるかは別問題。答えられなければUI表示の改善が必要。

テスト質問: 「このFindingのどこまでが今回取得したEvidenceで、どこからがAIの解釈ですか？」
回答者回答の要旨正しく区別できたか

4.7 運用安定性

Axis 04

機能開発を止めた今だからこそ確認する。今回のセッション中にも一度Azure接続エラーが発生している —— retry／resume／idempotencyが実運用で十分かは見ておく価値がある。

5

実施要領

3テーマそれぞれについて、同一の手順で旧フローとReport Studioを比較する。

CONTROL — 比較条件の固定

「Report Studio側だけ新しい情報を持っていた」という比較にならないよう、期間・入力・バージョン・評価時点を先に固定する。

STEP 1

旧フローで実施（ベースライン）

対象テーマを従来の手作業フロー（Prompt0〜Prompt2）で通し、成果物と各工程の所要時間を記録する。

STEP 2

同一期間データでReport Studioを実施

同じ期間・同じ入力データでReport Studioを実行し、Review Requiredの発生状況を含めて記録する。

STEP 3

専門家が両成果物を比較・採点

「4.1 Report品質」のルーブリックで採点し、修正箇所と重大度をログする。

STEP 4

工数を両条件で記録

「4.2 人間の作業量」の計測項目を両フローについて埋める。

STEP 5

運用ログを収集

「4.3〜4.7」を実運用ログ・ユーザーテストから継続的に収集する（4.4は2〜4週間の継続観測）。

6
